# 쿠팡이츠 사장님 리뷰 자동 답글 — 구현 가능성 검토

작성일: 2026-09-03

## 0. 결론 먼저

**기술적으로는 구현 가능합니다. 다만 "공식 API가 없어서 브라우저 자동화로만 가능"하고, 그 방식이 쿠팡 약관의 자동화 프로그램 금지 조항에 걸릴 소지가 있는 것이 핵심 리스크입니다.**

리스크의 크기가 문제입니다. 계정 정지 = 매장 매출 중단이므로, 기대 이익(답글 작성 시간 절약) 대비 최악의 손실이 비대칭적으로 큽니다.
그래서 **완전 무인 자동화보다, 사장님 브라우저에서 동작하는 "AI 초안 + 1클릭 승인" 방식(아래 안 B)을 1차 권장**합니다.

---

## 1. 사실 확인 결과

### 1-1. 공식 API 존재 여부 → **없음(확인된 범위 내)**

- 쿠팡이 공개하는 공식 오픈API는 **쿠팡 파트너스(제휴 마케팅)** 와 **쿠팡 마켓플레이스 셀러(Wing) OpenAPI** 두 갈래이고,
  **쿠팡이츠 사장님(입점 음식점)용 리뷰 조회/답글 등록 공개 API는 문서화된 것을 찾지 못했습니다.**
- 즉, 접근 경로는 사실상 **사장님 포털 웹(store.coupangeats.com) 또는 사장님 앱** 뿐입니다.
- 확정하려면 쿠팡이츠 파트너 지원센터(1600-9827 / eatspartners@coupang.com)에 **"POS·솔루션 연동용 API 제공 여부"** 를 직접 문의하는 것이 가장 빠릅니다. 이건 반드시 먼저 하시길 권합니다. 공식 연동 채널이 열려 있다면 아래 논의 전부가 불필요해집니다.

### 1-2. 이미 같은 걸 파는 상용 서비스가 여럿 존재 → **실현 가능성의 증거**

리뷰메이커, 리뷰오토, 리뷰플랜(다정디자인), 리프리, 리뷰매니저 등이 **배민·요기요·쿠팡이츠·땡겨요·네이버플레이스** 통합 자동 답글을 이미 판매 중입니다.
전부 공식 API 방식이 아니라 **크롤링/브라우저 자동화 기반**으로 보입니다. (= 만들 수 있다는 뜻이자, 동시에 그 방식밖에 없다는 뜻)

### 1-3. 약관 리스크 → **실재하나, 원문 미확인**

- 쿠팡 약관 개정 관련 보도에서 **봇·스파이더·스크래퍼 등 자동화 프로그램을 이용한 시스템 접근·데이터 수집 금지** 조항이 언급됩니다.
- **다만 이 검토 환경에서는 네트워크 제한으로 쿠팡이츠 사장님 약관 원문(`store.coupangeats.com/merchant/app/tnc`)을 직접 열어 확인하지 못했습니다.** 조항 번호와 정확한 문구는 반드시 직접 확인하셔야 합니다.
- 성격 정리: 본인 계정으로 본인 매장 데이터를 다루는 것이라 "무단 침입"류 이슈는 약한 편이지만, **약관 위반은 계약 위반이고 계정 정지의 근거가 됩니다.** (법률 자문 아님)

### 1-4. 플랫폼 기능 제약 (설계에 직접 영향)

- 리뷰 관리 메뉴에 **"미답변 / 답변" 필터**가 있음 → 작업 대상 선별이 쉬움. 유리한 점.
- **리뷰 1건당 사장님 답글은 1개만** 등록 가능. 고객의 재답글 불가.
  → **되돌리기가 어렵습니다. 잘못 달린 AI 답글은 그대로 공개 노출됩니다. 이게 자동화 설계의 제1 제약입니다.**
- 접속 경로: PC / POS / 스마트폰 웹 포털 + 사장님 앱.
- 로그인은 ID/PW 기반이며 **2단계 인증은 제공되지 않는 것으로 확인**(자동화에는 유리, 보안에는 불리).
- 답글 수정·삭제 가능 여부, 답글 작성 기한(작성 후 N일 제한) 은 **미확인 → 확인 필요**.

## 2. 구현 방식 3안 비교

| | A. 완전 무인 자동화 (서버 RPA) | **B. 브라우저 확장 + 1클릭 승인 (권장)** | C. 상용 서비스 구독 |
|---|---|---|---|
| 동작 | 서버가 ID/PW로 로그인 → 수집 → 생성 → 자동 등록 | 사장님이 직접 로그인한 브라우저에서 확장이 초안 생성, 사람이 확인 후 등록 | 업체에 계정 위임 |
| 계정 정지 리스크 | **높음** | **낮음** (사람이 로그인·최종 클릭) | 중간 (업체가 자동화 수행) |
| 계정정보 보관 | 서버에 평문급 보관 필요 → 유출 시 치명적 | **보관 불필요** | 제3자에게 제공 |
| 잘못된 답글 노출 | 막을 장치 없음 | 사람이 걸러냄 | 업체 정책에 의존 |
| 개발 공수 | 2~3주 + 상시 유지보수 | 1.5~2주 | 0 |
| 운영비 | 서버 + LLM 토큰 | LLM 토큰만 | 월 구독료 |
| 셀렉터 변경 시 | 서비스 중단 | 서비스 중단(동일) | 업체가 대응 |

**권장 경로:** `1600-9827에 공식 API 문의` → 없으면 → **B로 시작** → 운영 데이터 쌓인 뒤, **별점 4~5점 + 무클레임 리뷰에 한해서만** 반자동 → 완전자동 확대 검토.

## 3. 시스템 설계안 (안 B 기준)

```
[Chrome Extension]                       [로컬/경량 서버]
 리뷰 페이지 DOM 파싱 ──리뷰 텍스트만──▶  답글 생성 API
        ▲                                    │
        │                              Claude API (claude-opus-5 / sonnet)
   초안 표시 + 편집                          │
        │                              ┌─────┴─────┐
   사장님 [등록] 클릭 ◀──초안 반환──── 톤앤매너 few-shot
                                       금칙어/PII 필터
                                       위험 리뷰 분류기
```

### 3-1. 파이프라인

1. **수집** — "미답변" 필터 페이지에서 리뷰 ID / 별점 / 본문 / 주문 메뉴 / 작성일 파싱
2. **분류(가장 중요)** — 자동 처리 가능 여부 판정
   - 자동 초안 OK: 별점 4~5, 단순 칭찬/무텍스트
   - **반드시 사람 확인**: 별점 1~2, 위생·이물질·알레르기·환불·배달사고·법적 표현("신고", "고소", "식약처") 키워드 포함, 개인정보 언급
3. **생성** — 기존 사장님 답글 20~30건을 few-shot으로 넣어 톤앤매너 학습. 길이·이모지·인사말 규칙 고정
4. **검수 게이트** — 금칙어, 과도한 약속("전액 환불해드립니다"), 개인정보 노출, 최대 길이 체크
5. **등록** — 사장님 승인 클릭. `review_id` 기준 멱등 처리로 중복 등록 차단
6. **로깅** — 등록 이력 SQLite 저장, 실패 시 알림

### 3-2. 필수 안전장치

- **낮은 별점은 절대 자동 등록 금지.** 악평에 어긋난 AI 답글이 달리면 그 자체가 2차 사고입니다.
- **답글은 1회만 가능 = 롤백 불가** → 등록 전 확인이 유일한 방어선
- 사실 단정 금지(원인·보상 확정 표현 차단), 고객 개인정보 재언급 금지
- **탐지 회피 목적의 우회는 하지 않음** — 우회를 해야 굴러가는 구조라면 애초에 안 B로 가야 한다는 신호입니다

### 3-3. 기술 스택

- 수집/등록: **Chrome Extension (MV3, content script)** — 안 A라면 Playwright + Chromium
- 생성: **Claude API** (`claude-opus-5` 또는 `claude-sonnet-5`, 비용 고려 시 sonnet)
- 저장: SQLite
- 스케줄: 확장은 사장님 접속 시 동작 / 안 A는 cron 하루 2~3회

## 4. 착수 전 반드시 확인할 것 (이 환경에서 확인 불가했던 항목)

1. **쿠팡이츠 사장님 약관 원문** — 자동화 프로그램 금지 조항 유무·문구 (`store.coupangeats.com/merchant/app/tnc`)
2. **공식 연동 API 제공 여부** — 파트너 지원센터 1600-9827 / eatspartners@coupang.com
3. **리뷰 페이지 실제 네트워크 요청** — DevTools Network 탭에서 XHR/JSON 엔드포인트 존재 여부와 응답 스키마 (DOM 파싱보다 훨씬 안정적)
4. **로그인 시 캡차/이상행위 탐지 유무**
5. **답글 수정·삭제 가능 여부**, **답글 작성 기한**
6. **다매장 운영 여부** — 계정당 매장 수, 매장 전환 UI

## 5. 공수 산정 (안 B 기준)

| 단계 | 산출물 | 기간 |
|---|---|---|
| PoC | 리뷰 목록 파싱 + 초안 1건 생성 표시 | 2~3일 |
| MVP | 분류기 + 검수 게이트 + 승인 UI + 이력 저장 | 1.5~2주 |
| 안정화 | 셀렉터 변경 대응, 알림, 톤 튜닝 | 상시 |

상용 서비스가 월 수만 원대인 점을 감안하면, **자체 개발의 실익은 "톤앤매너를 내 손으로 통제하고 계정정보를 외부에 안 넘기는 것"** 에 있습니다. 단순 비용 절감이 목적이라면 안 C가 더 합리적입니다.

## 6. 요약

- 만들 수 있다 — 다만 공식 API가 없어 **웹 자동화가 유일한 길**
- 가장 큰 리스크는 기술이 아니라 **약관 위반에 따른 계정 정지**
- **안 B(사장님 브라우저 + AI 초안 + 사람 승인)** 가 리스크/효용 균형이 가장 좋음
- 착수 전 **공식 API 문의 + 약관 원문 확인 + DevTools로 실제 요청 확인** 3가지를 먼저
